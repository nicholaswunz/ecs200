Week 1: Quality checks and data exploration

In this workshop you will learn how to check the quality of raw data after you import it into R, and how to fix common errors. Workshop materials are available in the GitHub repository ECS200.

All statistical techniques have in common the problem of ‘rubbish in, rubbish out’.

TipLearning outcomes

By the end of this workshop you should be able to:

  1. Check that each column of a dataset has been imported as the right type.
  2. Find and deal with missing values, duplicates and inconsistent labels.
  3. Use plots to find outliers and decide whether they are errors.
  4. Save a cleaned dataset for later analysis.

Background

How do we know the data are ready for analysis? Before any analysis, check the raw data for the following:

  • Data structure and types: is each column the type you expect (number, category, text, date)? Use str() or dplyr::glimpse().
  • Missing values: where are they, and how many? Use colSums(is.na()) or visdat::vis_miss().
  • Duplicates: are any rows accidentally entered twice?
  • Categorical variables: are categories spelt consistently (e.g. “Male”, “male” and “M” are three different categories to R)?
  • Outliers or impossible values: negative lengths, a 50 kg frog, a date in the future.
  • Column names: meaningful, with no spaces or special characters.
  • Extra rows or columns: notes, totals or empty columns copied from a spreadsheet.

These checks make sure your data are reliable and suitable for analysis, and they make you a trustworthy researcher.

The tidyverse

In this unit we use the tidyverse style of coding. The tidyverse is a collection of R packages for importing, cleaning, transforming and plotting data that share the same grammar, so once you learn one package the others feel familiar. It is widely used in ecology because ecological data are often large and messy, collected across space and time, and have replicates nested within sites.

  • Pipes
  • Tidy data

The pipe operator %>% passes the result of one step into the next step. Read it as “and then”.

Code 
data %>%     # start with your data, and then...
  step_1() %>%  # do the first thing, and then...
  step_2()      # do the second thing

# Without pipes you read from the inside out
mean(log(c(1, 10, 100)))

# With pipes you read from top to bottom
c(1, 10, 100) %>%
  log() %>%
  mean()

Pipes make ecological workflows easier to read, because analyses usually involve several steps: import data, filter sites, remove missing values, calculate summaries, plot results.

Note

You may also see the “native” pipe |>. It does the same job. We use %>% in this unit because you will see it in most online help.

The tidyverse works best when the data look like this:

  • Each row is one observation.
  • Each column is one variable.
  • Each cell is one value.

Step 1: Data quality check

1.1. Initial check

First, check that every variable was imported as the right type. Common problems include:

  • Incorrect data types: a numeric column is read as text (chr) because it contains a symbol, a word, a comma instead of a decimal point, or an empty string.
  • Inconsistent coding: one category spelt several ways (“Male”, “male”, “M”), which R treats as different categories.
  • Header issues: a missing header row, or extra rows of notes at the top or bottom of the file.
  • Encoding problems: special characters (e.g. °, µ, accents) that display incorrectly.
  • Trailing spaces: “site A” and “site A” are different to R.

Fixing them in R is better practice, though, because the code records exactly what you changed. For example, suppose you have three sites (A, B and C) but one was mislabelled “E”. dplyr::if_else() replaces values that match a condition:

1.3. Checking duplicates

There are two kinds of duplicates:

  1. Row duplicates: two rows are identical in every column. This is almost always an error (e.g. copy and paste) and should be removed.
Code 
# Number of rows that are exact copies of an earlier row
sum(duplicated(plant_calcium_data))
[1] 0
Code 
# Show the duplicated rows (none here, so this returns an empty table)
plant_calcium_data[duplicated(plant_calcium_data), ]
# A tibble: 0 × 11
# ℹ 11 variables: year <dbl>, watershed <chr>, elevation <chr>, transect <chr>,
#   sample <dbl>, stem_length <dbl>, leaf1area <dbl>, leaf2area <dbl>,
#   leaf_dry_mass <dbl>, stem_dry_mass <dbl>, corrected_leaf_area <dbl>

There are no duplicated rows in plant_calcium_data.

  1. Value duplicates: the same value appears more than once in a column. This is usually real (e.g. two seedlings with a leaf mass of 0.03 g, especially after rounding). Be suspicious if there is a pattern, e.g. 2, 2, 6, 1, 2, 2, 9, 4, 2, 2, which suggests values were copied into the next row by accident. You, the researcher, have to decide whether duplicated values are real.
Code 
# Number of values in leaf_dry_mass that repeat an earlier value
sum(duplicated(plant_calcium_data$leaf_dry_mass))
[1] 51

There are 51 repeated values in leaf_dry_mass, which is expected for masses rounded to four decimal places.

Step 2: Visualising data

2.1. Check for outliers

Outliers are not automatically “bad”, but they can cause problems. They can:

  1. Distort results: a single extreme value can drag the mean, inflate the variation, and change the slope of a regression line.
  2. Hide patterns: one extreme value squashes the rest of the data on a plot.
  3. Reveal errors: data entry mistakes (typing 1000 instead of 100), faulty equipment, or mixed-up units (metres and centimetres).

Two simple plots will reveal most outliers.

  • Boxplot
  • Histogram

ggplot2::geom_boxplot() draws a boxplot. Points beyond the whiskers are potential outliers (more than 1.5 × the interquartile range from the box).

Code 
# Boxplot of leaf2area to look for potential outliers
ggplot2::ggplot(plant_data_clean, ggplot2::aes(y = leaf2area)) +
  ggplot2::geom_boxplot(fill = "lightgrey") +
  ggplot2::labs(y = "Area of leaf 2 (cm²)") +
  ggplot2::theme_bw()

ggplot2::geom_histogram() shows how the values are distributed.

Code 
# Histogram of leaf2area to look for potential outliers
ggplot2::ggplot(plant_data_clean, ggplot2::aes(x = leaf2area)) +
  ggplot2::geom_histogram(bins = 30) +
  ggplot2::labs(x = "Area of leaf 2 (cm²)", y = "Count") +
  ggplot2::theme_bw()

There is one clear outlier above 100 cm2. Every other leaf is smaller than 25 cm2. You can list potential outliers with the interquartile range (IQR) rule:

Code 
# Quartiles and interquartile range of leaf2area
q1  <- quantile(plant_data_clean$leaf2area, 0.25)
q3  <- quantile(plant_data_clean$leaf2area, 0.75)
iqr <- q3 - q1

# Rows with leaf2area more than 1.5 x IQR below Q1 or above Q3
plant_data_clean %>%
  dplyr::filter(leaf2area < q1 - 1.5 * iqr | leaf2area > q3 + 1.5 * iqr)

The IQR rule flags a few leaves, but only the 100 cm2 leaf is biologically unrealistic for a sugar maple seedling, so it is almost certainly a data entry error. Always use your biological knowledge (and the literature) to decide. Do not remove values just because a rule flags them.

2.2. Are the data normally distributed?

Many statistical tests (t-tests, ANOVA, linear regression) assume that the data (or, more precisely, the model’s residuals) are roughly normally distributed, with constant variance. If the data are strongly skewed, have outliers or have unequal variances, those tests can give biased estimates and wrong conclusions. You will learn how to check this properly in Weeks 5 and 7, and how to transform data in Week 2.

Let’s look at leaf2area again after removing the impossible value.

Code 
# Remove the data-entry error (the one leaf above 100 cm2)
plant_data_clean <- plant_data_clean %>%
  dplyr::filter(leaf2area < 100)

ggplot2::ggplot(plant_data_clean, ggplot2::aes(x = leaf2area)) +
  ggplot2::geom_histogram(bins = 30) +
  ggplot2::labs(x = "Area of leaf 2 (cm²)", y = "Count") +
  ggplot2::theme_bw()

The distribution is now roughly symmetrical and bell-shaped.
